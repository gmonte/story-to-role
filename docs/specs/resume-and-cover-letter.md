# StoryToRole spec: Resume and cover letter generation

Draft. Decisions are recorded here as they close; open points are listed at the end. Screening, generation and the coverage review follow the meu-emprego-novo method (its steps 03, 04, 04b and 05), from the user's profile ([profile-truth.md](./profile-truth.md), [ADR 0008](../adr/0008-profile-truth-is-the-source-of-truth.md)).

## Goal and scope

For one opening, StoryToRole generates a tailored resume and cover letter from the published version of the user's profile, frozen in each document it produces, plus any application instructions the user adds. The AI invents nothing: what the opening asks for and the profile doesn't show is a declared gap. What the user states is the user's responsibility (ADR 0001).

Hiring interview prep is out of the MVP.

## Openings and library documents

- An opening always has someone on the other side: a posted vacancy, or a company the user wants to approach with no vacancy open (for example, a cover letter for Airbnb). Openings of either kind can become applications and appear in the tracker.
- An unsolicited opening (no vacancy) requires only the company; the intended role or area, free notes and links are optional. With no requirements to compare, the fit check does not run, but the opening's vector (company, role, notes) still suggests similar library documents, and the intended role feeds `<Title>` in file names. It starts open and the user can close it, for example when the company replies that it has no vacancies.
- A **library document** is a resume or cover letter with no company behind it, generated from the published profile with the method's prompt 04 (a new version for a family of openings). A user can keep several, each with a required **focus** that serves as its title: a stack or kind of role ("React Native", "React Web", "Frontend", "Full-stack Node"), or "General" for one that presents each position's strongest points. In the interface, the Library lists them by focus, with plain "New resume" and "New cover letter" actions. Library documents live outside any application, use the same versions, snapshots, undo, adaptation and language sync, skip the fit check and never appear in the tracker. Generating one does not start an application.

## Flow

1. The user adds an opening by pasting its description. Code first checks that the text looks like a job posting.
2. StoryToRole runs a **fit check** automatically, the method's screening (step 03), and shows it as a hint, never as a gate. A small AI call extracts the opening's keywords (hard skills, tools, certifications, languages) and requirements (seniority, years of experience, location, work model). Each keyword and requirement retrieves the closest passages of the published profile by vector similarity (ADR 0004); a cheap AI call then judges each one as met, partial or a gap, seeing only the requirements, the retrieved passages, the profile's overview (each position's title, employer and period, credentials and languages, from which years and seniority are read), the profile's declared gaps and the user's job preferences, never the whole profile. A competency marked "studied", anything under "what I did not do" and the known gaps count as gaps, never as coverage: those lines are never retrieved as passages, code makes a gap of a short requirement that a competency only studied or a short gap line names, and for the rest the judge points at the line that says so. Vector similarity alone does not decide, since it misses seniority ("8+ years" against a junior history reads as similar) and hard requirements such as location or language. The hint shows the method's band:
   - **High:** covers the mandatory requirements with profile passages behind them, and the work model and location are acceptable.
   - **Medium:** covers most of them; what is missing is desirable or can be learned.
   - **Low:** a mandatory requirement is missing, or the opening breaks one of the user's job preferences.

   Code decides the band from the verdicts. An opening that names nothing as mandatory is read by how much of what it asks the profile covers (met counts whole, partial half): high from three quarters, medium from two fifths. Location and work model are answered by the job preferences; with none published they are shown as unknown and left out of the band.

   Each requirement is linked to the passage that backs it ("without a passage, a verdict is an opinion"), and the main gaps are listed; there is no percentage score, which would claim a precision the analysis does not have. The method's warning signs (a description too vague to identify the company, contact only through a messaging app, a pay promise far above the market with no requirements, a request for payment or sensitive data before any conversation, a test that requires downloading and running code outside known platforms) show as a warning on the opening, with or without a fit check. It counts as an evaluation in the plan, separate from generation. The job preferences document (work model, locations, salary range, excluded companies and sectors, discard rules) is read only here, never by generation. A broken preference is found by code where it can be (an excluded company by its name, an excluded sector the posting names) and otherwise by a small AI call that sees only the opening and the preferences, each line numbered, and answers with the numbers of the lines the opening breaks. With no profile published yet, the opening is kept and the fit check waits until the user publishes and runs it; a fit check made on an older version of the profile or of the preferences says so and can be run again. Running it again reads the opening's stored requirements, not the opening's text, and keeps the answers already given to its gap questions.

3. Next to the fit check, StoryToRole suggests existing documents similar to this opening, ranked by vector similarity between the opening and each document: library documents and documents from other applications, including ones already sent.
4. Whatever the fit check says, the user may get a resume, a cover letter or both, each only on demand, in one of three ways:
   - **Use as is:** the latest snapshot of the chosen document's version is copied as the first snapshot of this application's document. No AI call is made. If the chosen document is in another language than the output language, it is copied and adapted instead, following the adaptation rules; this makes an AI call and counts as a generation, which the user is told before confirming. The source document does not change.
   - **Adjust** (the method's prompt 04b): a new document for this opening starting from the chosen version of the same family, changing only what is needed (see Generation rules). The user reviews the result. The source document does not change.
   - **Generate a new version** (the method's prompt 04) from the published profile.
5. The application starts when the first document is generated or copied for the opening. Openings that were analyzed but never generated for stay in a list of analyzed openings, outside the tracker.

## Embeddings

Embeddings are part of the MVP.

- Vectors exist for every passage of the published profile (recomputed on publish, only for what changed), document (the latest snapshot of each version), opening and opening keyword. An opening's vector is computed as soon as it is added, whether or not the user has documents yet.
- They are computed by a local multilingual embedding model running in a Trigger.dev task, since an opening may be in English while the profile is in Portuguese. No AI vendor receives the text for this.
- They are stored with pgvector in the application's Postgres database.

## Review rounds

Generating a resume runs a loop: a strategist drafts, a reviewer judges the draft's **coverage** against the opening (or the library document's focus) and the frozen profile, the same blocks as the coverage review (strong coverage, partial coverage, gaps not invented, inconsistencies), and an editor applies the review, only reordering and rewording to cover better what the profile states, never covering a gap. Each **review round** (review plus edit) rewrites the whole document, which makes rounds the largest generation cost. The loop stops when coverage no longer improves.

- **The resume score (shown as “Resume score N/10”) measures only the match.** Strong coverage counts whole, partial half; contradictions never lower it (there is no cap). They are counted apart and shown beside the score (“N points disagree with your profile”), each with the exact quote from the resume and the profile line it contradicts. Each reviewer writes its feedback in the user's interface language (the profile's language); requirements stay as the opening wrote them.
- **What a contradiction is.** The resume states something the profile denies or doesn't support: a wrong fact (date, employer, title, city, education); a figure the profile lacks or states differently; overstated authorship; something the profile says the person didn't do, or an unknown result stated as certain; a wrong nature (a personal project as a job, an unlaunched project as launched); a tool the profile doesn't mention in that context. Not a contradiction (advice, or nothing): slightly stronger but compatible wording, an omitted caveat, a faithful paraphrase, organisation, language or spelling, coverage. Doubt test: if someone who knows only the profile would say “that's not true”, it is a contradiction; if “true, but I'd put it differently”, it is advice. None is the usual answer.
- **Proof.** Each contradiction is `{ quote, profileLine, kind }`; code drops one whose quote isn't found in the draft (ignoring whitespace, accents and case). Reviews stored as plain strings still display, as text only.
- **Selection.** A draft with contradictions is never kept over one without; among equals, the one within its pages, then the best-rated. Thorough never stops early on a draft with contradictions, and a contradicting draft's round is passed to the editor to correct.

- The user picks the depth before generating: **Quick** (one round) or **Thorough** (up to three rounds, stopping early when coverage stops improving). The best version is kept: no contradictions first, then the highest rating. Each option shows its credit estimate.
- The number of rounds behind each option is a setting, not a constant, so it can be tuned with real data.
- Every round's rating, cost and outcome are stored, so the quality gained per extra round can be measured.

## Generation rules

From the method's prompts 04 (a new version) and 04b (an adjustment), checked in code where they can be:

- The frozen profile version is the **only** source of facts, contact data included; the opening (or the library document's focus) only says what to prioritize. The version published when the document is asked for is the one frozen, with the settings chosen in the form; nothing is generated before a profile is published. The header (name, email, phone, LinkedIn, website, city) is read from the profile's Professional identity and Contact sections.
- Every employer, title and date is preserved (locked facts, ADR 0001).
- No technology, figure, certification or responsibility the profile doesn't state.
- Figures only when the profile marks them `[medido]`; `[estimado]` and `[a confirmar]` figures never appear, `[sem número]` results appear as qualitative ones. Code withholds those figures from the writer (it reads the line without the number) and refuses a written line carrying a number its profile lines don't show as measured; a result's number with no mark at all is withheld too, while a number in a plain fact (a team's size) is a fact like any other. Marks never appear in a document. **Public names:** the profile's “Public names” line maps a real name to the form a document uses. The writer reads the real profile plus an instruction with the mapping, so it knows what each thing is; afterwards code only detects an original still in a line, then one small repair call (part of the generation, no extra charge) rewrites just those lines with the public form, adjusting the sentence around it (articles, gender, agreement), and code checks again. Never a blind substitution. An original that remains is a warning finding, not a block: the PDF, ZIP, copy and mark-as-applied stay available after the user confirms (“Generate PDF anyway”). An employer or title printed by code is written in its public form directly. Nothing the profile lists under "what I did not do" is ever claimed, and nothing on its communication rules' "never include" list appears (its literal terms by code, its categories as an instruction in the prompt in every public document: resume, letter, LinkedIn, adjustments and the coverage review): a profile line naming such a term is not handed to the writer, a written line carrying one is removed, a credential naming one is left out, and an employer naming one prints as "Confidential" (a title keeps what is left of it).
- Every resume and LinkedIn bullet (experience or project) follows the product's universal format: action, then impact, then how and with what. It is the same for every user, never shown in the interface, and defined in code (`writing/bullet-format.ts`); a bullet off it in a way code can tell gets an ignorable `bulletShape` warning, never a block.
- Bullets are reordered and rewritten to put first what the opening asks for; the opening's vocabulary is used only when it is true of the user.
- Certifications with their real status (valid, expired, in progress).
- A summary of 3 to 4 lines.
- A field with no information in the profile stays empty; nothing is inferred.
- **Adjusting (04b)** changes only the order of bullets, the order of competencies and the summary; it adds a bullet only when the fact is in the profile, and never tries to cover a gap the coverage review listed. Code guarantees it: the model names the existing bullets and competencies in a new order and never rewrites one. The result is in the language of the version it started from, and it runs no review round.
- After each generation, StoryToRole lists in up to five lines what it emphasized and what it left in the background; after an adjustment, what changed from the version it started from.

## Generation settings

Each user has global generation settings, shown as a form prefilled with them every time a document is generated; the user changes there whatever they want for that document only.

| Setting                                                               | Default                         |
| --------------------------------------------------------------------- | ------------------------------- |
| Bullets per recent experience (ended at most N years ago, or current) | 3                               |
| What counts as recent (N)                                             | 5 years                         |
| Bullets per older experience                                          | 2                               |
| Very old experiences (ended M years ago or more)                      | Left out, unless relevant       |
| M                                                                     | 10 years                        |
| Resume length                                                         | At most 2 pages                 |
| Cover letter length                                                   | At most 4 paragraphs and 1 page |

The user can also choose to always leave very old experiences out, or to keep them like older ones. A very old experience enters only when it matches the purpose of that document: it covers one of the opening's requirements, or the library document's focus, with the profile passage that proves it. It then gets one bullet, tied to that requirement, and the coverage review says why it entered.

Code enforces the settings on the structured content and again after rendering the PDF, for every generation and adaptation; a document the user edits by hand gets the length warning instead. "What counts as very old" must be more years than "what counts as recent". When a document runs over its length, it is shortened in this order: the bullet of a very old experience that entered for relevance; the bullets of older experiences, oldest first, removing an experience rather than leaving it with no bullet (a resume never shows an experience without bullets); the summary down to 3 lines; the competencies least related to the opening. The bullets of recent experiences are never cut: if the document still doesn't fit, the user is warned instead. A cover letter one paragraph too long is rewritten to fit.

## Coverage review

Every generated resume and cover letter comes with a coverage review (the method's prompt 05), checked against the profile version frozen in that document and included in the generation's price.

- **Code checks, exact:** employers, titles and dates preserved; the number of bullets and pages within the settings used for that document; every figure present in the profile and marked `[medido]`; no "never include" term; nothing from "what I did not do" claimed; a very old experience only with the requirement that justified it; every line traced to the frozen profile version (“not in your profile” otherwise). A failure is pointed out as a finding and never blocks the document (“Document workspace” below).
- **AI review:** the sources used; what was preserved; strong coverage (each requirement → the resume passage → the profile passage that proves it); partial coverage (requirements touched only indirectly); gaps not invented (requirements the document does not prove, listed by name); inconsistencies (any fact, date or figure that doesn't match the profile). Where the profile has no passage it says "no evidence in the profile". It never suggests covering a gap: it suggests reordering, or, for a true fact the profile omits, updating the profile, which opens it as a suggestion in the profile's draft. A document whose structure is broken gets a pointer to it; whatever code can fix, it fixes.
- It ends with the method's statement: "This review does not claim that every mandatory requirement is met." ("Esta revisão não afirma que todos os requisitos obrigatórios são atendidos.")
- The code checks run on each version's official snapshot whenever it is shown, against the profile version that snapshot was written from (the one published now for a document from before snapshots carried it). They count what the user wrote by hand too: a figure the user types that the profile doesn't mark `[medido]` is pointed out, and the way out is to mark it in the profile, reword the line or confirm past it. A position's years are locked facts a line may name. Pages count only once the PDF is rendered and measured; before that the editor warns on its estimate. Nothing blocks: downloading the PDF, the application's ZIP, copying a section and marking the application as applied ask for one confirmation (“Generate PDF anyway”) while findings are open, and a finding the user ignored asks for none; the account export is the user's own data and never asks.
- The AI review runs once per generation (a new version or an adjustment) and is not run again after edits; the version says when its review is of an earlier change. It judges the requirements a document can prove: location and work model are answered by the job preferences and stay out of it. A review that fails, or answers something that isn't a review, leaves the document saved without one, never with invented gaps. The very old experiences it lists come with the requirement they entered for.

## Gap questions

The profile is not rewritten for every opening: the goal is that, once it is published, the user only adds an opening and asks for a document. Before generating, StoryToRole turns each gap found by the fit check into a question, one per point: does the user have it, or not? Each answer is one of two, and either way the profile only changes when the user accepts the suggestion in My career and publishes.

- **I have it.** The user writes what they did and says where: a multi-select of the published profile's positions and projects, at least one, or "Not tied to a position" for something general. The answer is kept with the opening as an application instruction and also proposed to the profile (origin `application`, figures only as the user wrote them): one suggestion per chosen entry, adding the answer as a line under Responsibilities of a position or What I did of a project, and one under Seniority and areas of Professional identity for a general answer. After the user accepts and publishes, the fit check finds it. The screen says it was sent to the profile, with a link to My career.
- **I don't have it.** No position is asked. The lack is recorded on the opening and proposed as a line under Known gaps, in the user's words when they wrote any, else as the requirement ("No experience with X"); never under a position's "what I did not do".

**For this opening, without changing the profile.** The answers also count in this opening's fit check. When the user runs the check again (“Check again”), the judge reads the published profile plus this opening's answers: an “I have it” answer is evidence for its requirement (met or partial, judged as strictly as a passage), shown as “Your answer for this opening” and kept apart from the profile passages it does not replace; an “I don't have it” keeps the requirement a confirmed gap. The band is recomputed from that, at the usual credit cost of a re-run. The suggestions to the profile stay optional: accepting them keeps the fact for future openings. The answer's links (positions, projects, or not tied) are stored with it and fill the form again on reload. The resume and the letter already receive the answers as application instructions (one point per answer, at the next split), so they use them the same way; figures only as the user wrote them.

**Every gap and partial card is answerable**, with options that fit its kind (the card's own form, compact, no separate list):

- **A skill, tool or experience requirement** (including a gap the profile declares, which has no question): “I have it” (the story and where, as above) and “I don't have it”. A declared gap is entered as “This isn't a gap” and then follows “I have it”.
- **A condition** (category `condition`, plus location and work model: schedule or availability such as a start time, travel, contract type, start date, language level, salary): “I meet it”, “I don't meet it, but it's not a blocker for me” or “It's a blocker for me”, each with an optional note (for example “I can start at 7:00 if needed”). There is no profile sentence for a condition. For a blocker the user can also choose “Add to my job preferences”, which writes a discard rule (the requirement and the note) in the job preferences, like the withdraw dialog's “Add as a discard rule”. A condition has no gap question, and the answer can be taken back with Undo.

A condition answer is stored on the fit check item with the other answers (its stance, the note as the answer), shown on the card as “Your answer: …” with Edit and Undo, counts as the user's input for this opening (the resume and the letter receive it as an application instruction point; both document agents see it as a condition the person meets, doesn't meet without blocking, or finds a blocker), and makes the fit check read as outdated like any other answer. At the next check the judge reads “I meet it” and “not a blocker” as the user's answer for the requirement; a blocker is shown with a warning on the card and in the band card (“You marked 1 blocker”). Nothing re-runs by itself.

An answer can be edited or changed to the other kind later; a suggestion already sent stays in My career until the user rejects it there.

## ATS check

After a resume is generated for an opening, StoryToRole compares it against the opening's keywords (hard skills, tools, certifications, languages) the way an applicant tracking system reads it: literally, as the opening spells each term. The result is factual ("14 of 18 keywords"), and the missing keywords are split in two:

- **You have it, use the opening's term:** the profile states it under another spelling ("Postgres" for "PostgreSQL"); the user is advised to use the opening's term. A term is only suggested when a profile passage backs it.
- **Real gap:** no profile passage for it.

The ATS check applies to generated resumes only; it plays no part in suggesting similar documents.

## Application instructions

- On the generation screen, the user can add free-text instructions that apply to this application only: a detail they just remembered, a different framing of an old position, or experience that is not in the profile. They are saved with the application when its first document is generated.
- StoryToRole does not verify whether these statements are true.
- Right after the user writes them, before generating, the system splits the instructions into points and asks, point by point, whether each one should also go to the user's profile. The AI pre-selects points that look like new career facts ("I led the Kubernetes migration in 2021") and leaves unselected points that look like adjustments for this opening ("emphasize people management"); the user confirms. Points sent to the profile become suggestions in its draft, in the right section, for the user to accept and publish like any other; the others stay in this application only.
- An instruction that changes a locked fact (employer, title or dates of an experience) creates a **locked-fact override** for this application only. The system shows it explicitly ("In this application, your title at Company X will be 'Engineering Manager' instead of 'Tech Lead'") and asks for confirmation; code then enforces the new value in this application. Locked facts guard against the AI, not against the user: the AI still may not change any of them on its own.
- Lines generated from an instruction trace back to that instruction, as other lines trace back to their profile passage.

## Cover letter inputs

A cover letter follows its own methodology and draws on two inputs a resume does not have:

- **Company research:** on request ("Research company"), a separate task searches the web with the provider's web search tool, within a limit of searches, and returns a short list of **company facts**, each with its source link. The user selects which facts to use; only those enter the cover letter's context. Page text is third-party data, never instructions. The model that writes the letter still has no web access. Facts and their approval are stored with the application; there is no shared cross-user cache of company research, since caching the web is not viable. It costs credits, estimated before running.
- **Motivation interview:** three to five short questions, one at a time, by voice or text, about why the user wants this opening (what drew them to the company, how the role fits the moment of their career, any personal link to the product or mission). Answers are split into points like application instructions: points about this company stay in the application; points about the user ("I want to work on financial products", "I look for small teams") are offered, point by point, as suggestions for the profile's **career direction** (under Professional identity); a point joins it only after the user accepts it and publishes, so later letters ask less. Each answer costs about 2 credits. The user can skip it; the letter is then marked "could improve with your motivation".
- **Story choice:** StoryToRole ranks the stories told in the profile's experiences (a challenge, the user's choice and its outcome) by similarity to the opening's requirements and shows the top three, each with a line on why it fits; the user picks one. When the chosen story lacks a turning point or detail, the motivation interview adds one or two questions about it ("when did you have to decide?"), and the answers become suggestions for that experience in the profile's draft, used once the user accepts them.

**Methodology: storytelling.** Based on Braven's "The power of storytelling in your cover letter" (braven.org, 2019). The letter is built around one convincing story, not a list of skills:

1. **Opening:** an attention-getter tied to the letter's topic (a concrete fact about the company, a tagline, a short quote) that leads smoothly into the story. No stock greeting such as "I am writing to apply for".
2. **Story:** one past experience that exemplifies the skills and attributes the opening asks for, told as a plot: the setup, the build-up, the turning point and the final result. It must be clear about "the challenge, the choice you made, and the outcome", add something the resume does not already say, and show how the user would fit the company's culture. "Pick one story and stick with the highlights."
3. **Conclusion:** amplify the impression, connect the story to the role, express interest in talking (interview, follow-up, contact) without sounding needy or arrogant, and close formally.

Rules: about one page; personal, honest and enthusiastic; every sentence earns its place; no template phrasing ("hiring managers can sniff a template from a mile away"); no embellishment. The story comes only from the frozen profile and the user's own words, and company facts only from approved research, so the letter invents nothing; its figures follow the same rules as a resume's. Its length follows the generation settings (at most 4 paragraphs and 1 page by default), and its tone the output language's conventions in the tested language list. It gets the same coverage review as a resume.

## LinkedIn

The method's step 09, decided with the owner: StoryToRole writes the user's LinkedIn texts from the published profile; it does not read or compare the current LinkedIn profile, and it never changes anything on LinkedIn (the user copies what they approve).

- **Its own page:** **LinkedIn** is the sidebar's second item, right after My career ([workspace.md](./workspace.md)); the library no longer lists it. With no text yet, the page explains what it writes and offers **Generate my LinkedIn** (the output language, writing level and tone, as today). Once generated it opens in the document workspace below, like the profile: the index of its sections and the findings on the left, the texts edited in blocks in the center, and on the right the agent and the versions.
- **What it holds,** in LinkedIn's own order, each section with a **Copy text** action:
  - **Headline:** 3 to 5 options the AI writes (each at most 220 characters, LinkedIn's limit: how the person defines themselves professionally, their main area and what they bring, as the profile states it; never a figure the profile doesn't mark `[medido]`). The first is chosen; the user picks another with one click and edits the chosen one. Only the chosen headline is copied and checked; an option longer than 220 characters is not kept.
  - **About:** what a recruiter scans in 20 seconds and searches by keyword: in the first person, 3 to 4 short paragraphs, 150 to 300 words and under 2,600 characters (LinkedIn's limit), no bullets, headings or emoji. An identity line (title, years of experience only when the profile states them, what the person delivers, the main platform or domain); the proof (each achievement as what, how and impact; one paragraph per employer, most recent first, opening with the environment's scale, or the one or two strongest achievements early in a career); and a closing keyword line (“My strongest areas are …”, 8 to 15 competencies the person uses) with the key certifications and the direction the profile states. Numbers replace adjectives: no filler or self-praise (“dynamic”, “passionate”, “proven track record”…). The rule lives in code (`aboutFormatRule`) and the document agent follows it too; as a summary-like line, the whole About is still dropped when it carries a figure its cited lines don't show measured or names a competency only studied.
  - **Experiences:** every position, new or old, with its key achievements in 3 to 4 bullet points in the resume's bullet format (fewer only when the profile holds fewer facts). A LinkedIn text has no page limit, so none of the generation settings apply to it (bullets per experience, recent and very old experiences, pages) and its form doesn't show them. Employer, title and dates printed by code.
  - **Projects:** each project of the profile's Projects section for LinkedIn's Projects section (name, role, dates and link printed by code; its description in 3 to 4 bullets by the same rules).
  - **Education:** each education credential of the profile (course, institution and period printed by code) with an optional short description the AI writes only when profile lines back it (a thesis, an honour, a project done there); with none it has no description, and the user may write one.
  - **Certifications:** printed by code from the profile, as LinkedIn's form asks for them (name, issuer, date, status); no AI.
  - **Languages:** printed by code from the profile, each with its level converted to LinkedIn's fixed scale (Elementary, Limited working, Professional working, Full professional, Native or bilingual proficiency; pt-BR “Nível básico”, “Proficiência limitada”, “Proficiência profissional”, “Proficiência profissional completa”, “Proficiência nativa ou bilíngue”): CEFR A1–A2 and “básico” as Elementary, B1 and “intermediário” as Limited working, B2 and “avançado” as Professional working, C1, C2 and “fluente” as Full professional, “nativo” and “bilíngue” as Native or bilingual. A level the conversion can't read keeps the profile's words, and the user picks the scale's level in the editor.
  - No keyword lists and no skills section.
- **Generated at once, redone by parts:** **Generate my LinkedIn** writes every section in one generation (one writer call, then the coverage review), charged as a generation. Afterwards each AI-written section (the headline options, the About, one experience, one project, one education's description) has **Generate this section again**, which rewrites only that section from the frozen profile version, priced as an adjustment, and becomes a new snapshot: the other sections, and the user's edits in them, stay as they are. A regenerated section gets the code checks at once; the AI coverage review stays the last one until the user asks for **Review again**.
- **Like any document:** one LinkedIn document per user, with versions per output language, snapshots, undo and edits; generating again makes a new snapshot. Everything is the user's to edit except the code-printed facts (employer, title and dates, a project's name and dates, the education, certification and language records); an edit that makes a line differ from the profile follows the document workspace's rules (“not in your profile”, never refused).
- **Same rules:** the frozen profile version is the only source of facts; locked facts are printed by code; figures only when marked `[medido]`; communication rules and "what I did not do" apply; it gets the coverage review (code checks that ask for a confirmation before copying, and the AI review against a general purpose: the person's career as the profile states it).
- **The agent:** the document agent (ADR 0009) works on the LinkedIn text as on a resume: it reads the frozen profile version, takes a selected passage or a finding as an attachment, and every change it makes is a suggestion in the text (Accept, Reject).
- **Cost:** the whole text is charged as a generation and one section as an adjustment, each estimated before running.

## Cover letter and its resume

- A cover letter can be generated without a resume, but it is more accurate when generated from one.
- When generating a cover letter, the most recently changed resume version in the same output language is preselected if one exists; the user can pick another version of the resume or generate without one.
- A cover letter generated from a resume records the exact resume snapshot it used. When that resume version later gets a new snapshot, the cover letter is marked **outdated**, with a notice that the resume changed after the letter was generated. Changes to other versions of the resume do not affect it.
- The notice offers two actions: **Update the cover letter** (primary), which adjusts only the passages affected by what changed in the resume since the snapshot it used, keeps the user's own edits, and is reviewed before becoming a snapshot; and **Generate again**, which rewrites the letter from the current resume (the old content stays in history). The user may also keep the letter as it is and dismiss the notice.

## Output language

- The user picks the output language before generating. It is preselected from the language detected in the opening description.
- Output languages come from a tested list, starting with English and Brazilian Portuguese; each new language is added only after testing, with its market's conventions (date formats, section names, expected length) configured.
- No resume includes a photo, age or marital status in the MVP, whatever the market's custom. A user who wants that kind of information asks for it in one opening (as an application instruction) or in their global template.
- **Code-printed fields in another language.** A document in a language other than the profile's (English from a Portuguese profile, or the reverse) prints the fields code copies from the profile through two dictionaries, in every generation, adaptation and LinkedIn text. The **Languages** lines go through a small built-in dictionary (language names and the common level words, Brazilian Portuguese ⇄ English: "Português (nativo)" prints as "Portuguese (native)", "fluente (C1)" as "fluent (C1)"; CEFR codes and unknown words stay as written), as does a credential's status ("válida" / "valid"). The profile's **translations dictionary** ([profile-truth.md](./profile-truth.md), "Communication rules") then applies its exact, whole-field entries (case aside) to the employer and its note, the title (beside the approved title equivalents below), the education course and institution, the certification names, the city line and, where it names one, the public-names output. Entries change wording only; a figure is never touched. A field left in the profile's language (heuristic: it still holds a word of that language's stoplist or of the built-in dictionary; a proper noun alone is never pointed out) gets the warning finding **"Not translated: …"** with **Add translation**: a small form, the field prefilled and the default being the field itself (no AI), that proposes the entry in the profile's draft as a suggestion (origin `document`), like "Add to the profile"; once published and "Use version N" applied, the document prints it. The user may also just edit the field in the document. Nothing blocks.
- After generating, the user can ask for a document in another output language at any time, which creates a new version of that document. Every snapshot is kept. Two choices are offered, kept few on purpose so they stay clear to non-technical users: **Adapt from** an existing version (the default; same content rewritten for the new language, priced as an adjustment) or **Generate a new version** from the profile (priced as a generation). Only adaptation (and recreating, which is an adaptation) links the two versions for language sync; a version generated from scratch is independent.

## Adaptations

A snapshot in another output language is an **adaptation** of an existing snapshot, not a literal translation and not a fresh generation.

- It keeps the same profile passages and the same trace for every line.
- It rewrites wording for a native reader of that language and market: idiomatic action verbs, section names, date and number formats, and the opening's keywords in that language. Phrasing that does not work in the target language is reworked rather than translated word for word.
- It adds no new fact and never converts figures (no currency conversion, which would invent an exchange rate).
- The same code checks as any generation apply: locked facts, figure marks and the communication rules' "never include" terms.
- **Titles in another language:** the first adaptation into a language proposes an equivalent for each position's title ("Analista de Sistemas Sênior" becomes "Senior Systems Analyst"); the user approves or edits it once, and that version becomes a locked fact of the experience in that language, and can also be saved as an entry of the profile's translations dictionary ("Also save it in my profile's translations", a suggestion in the draft). A title the dictionary already translates gets no proposal. Code then accepts either the original or the approved title. Company names are never translated, but an employer's note is, through the dictionary ("Meta IT (agora Insi)" → "Meta IT (now Insi)"), as are the education, certification, city and language lines ("Output language" above): an adaptation prints those fields again in the target language.
- Generating again from the profile in the new language remains available as a separate action.

## Versions and snapshots

Documents are versioned like a git history, stored as rows in Postgres rather than in a git repository. In git terms, a version is a branch and a snapshot is a commit.

- An application has up to two **documents**: a resume and a cover letter.
- Each document has one or more **versions**, created only when the user asks for it. Each version has an output language and its own line of snapshots; a document may hold several versions in the same language. When the user asks for a version in a language the document already has, StoryToRole asks whether they really want another one. Versions are independent of each other, and the resume and the cover letter are independent of each other.
- **Duplicate** creates a new version in the same document from the latest snapshot of the current one, for example to keep a safe copy while experimenting. A duplicate is independent: it is not linked for language sync.
- Every change to a document creates an immutable **snapshot**: a full copy of the structured content, its parent snapshot, its origin (generated, adapted, edited), its author (user or AI) and its time. Diffs between any two snapshots are computed when shown.
- The **latest snapshot of each version is the official one**. There is no manual "current" marker; the history exists so actions can be undone.
- Snapshots behave as a stack. **Undo** deletes the latest snapshot, making the previous one official; a snapshot below the top cannot be deleted on its own. Restoring an old snapshot creates a new latest snapshot with that content.
- The user can delete a whole version, which deletes all of its snapshots and any cached files rendered from them. There is no archive: deletion is final and asks for confirmation.
- Side effects of deletion: when the snapshot a language sync would use as its base is gone, the sync uses the nearest remaining ancestor, or offers to recreate when none is left; when the resume snapshot a cover letter was generated from is gone, the letter is treated as generated without a resume; when a version that another one was adapted from is gone, the other one simply continues on its own.
- An adaptation takes the latest snapshot of one version as its base and writes the result either into a new version or into an existing one. Into an existing version it **recreates** it: the result becomes its new latest snapshot, replacing its content (edits made only in that version are not carried over). Earlier snapshots stay in history, so recreating can be undone. Example: after many edits in English, the user recreates the Portuguese version from the English one.

## Language sync

When one version of a document has changes that another version of the same document has not received, the behind one is marked outdated ("Outdated relative to Portuguese: 3 changes"). Nothing changes on its own.

- On demand, **language sync** carries the same ideas into the target by a three-way merge: the base is the source snapshot the target last came from (by adaptation or a previous sync), the source is the source's latest snapshot, and the target is the target's latest snapshot, whose own edits are preserved.
- The changes found in the source are listed one by one, all selected by default; the user unselects any they do not want. One AI call then adapts the selected changes into the target.
- Where both sides changed the same passage, both are shown and the user chooses.
- The result is a proposal: the user reviews the diff and accepts or discards it. Accepting creates a new latest snapshot in the target, which records the source snapshot as its new base.
- It works in any direction, always within one document (resume to resume, cover letter to cover letter). Recreating from another version remains the alternative when the user wants to replace everything.

## Submission record

- When the user marks an application as applied, they say which versions of each document were sent; the application records the exact snapshot of each, which shows as "sent" in the change history.
- Documents are never frozen: the user keeps editing, syncing and undoing as before, and since snapshots are immutable the sent content stays intact. Marking applied by mistake is undone by changing the status back.
- Deleting a version that holds a sent snapshot asks for confirmation; afterwards the tracker shows "sent version deleted". Deleting an application or the account always deletes everything, sent snapshots and cached PDFs included.
- Reusing a document from another application as a starting point works the same whether or not that application was sent.

## Interface wording

The interface calls snapshots "changes" ("alterações" in Brazilian Portuguese): "Change history", "Restore this change". Each version is shown as a tab named by its language, with a short label when a language repeats ("Portuguese", "Portuguese · copy"), which the user can rename.

## Rendering

Documents are downloaded as PDF only, in every plan, with no watermark. There is no DOCX export: edits stay inside StoryToRole, where every change is a snapshot and every line keeps its trace to the profile, instead of drifting into a file edited elsewhere. PDFs are rendered on demand from a snapshot's structured content. Since snapshots are immutable, a rendered file never goes stale: it may be cached in private Vercel Blob storage keyed by snapshot and template, and the cache can be purged at any time without losing anything. File storage (this cache and uploaded files) sits behind a small interface (put, get, delete). An explicit `STORAGE_DRIVER` environment variable selects the implementation: `vercel-blob` (the default) or `local`, which writes to a git-ignored folder so development works offline without a token. The app refuses to start when `STORAGE_DRIVER=local` is set with `NEXT_PUBLIC_ENV` other than `development`, and it never falls back to local storage on its own (for example when the Blob token is missing); `.env.example` ships with `local`. A quick test against a real Blob store runs before release, since the production driver does not run in development. Each section of a document (summary, each position, the whole cover letter) also has a **Copy text** action, for application forms that ask for pasted text; no editable file leaves the platform. Markdown and DOCX exports are not offered; DOCX may come back only for a concrete case of an opening that requires it. File names follow two conventions, each for a different reader. A single PDF is named for the recruiter who receives it, so they recognize whose document it is at a glance; the application ZIP is named for the applicant, to keep their uploads organized by opening. PDF file names use the fixed words in the document's output language:

- Resume: `<FirstName>_<LastName>_<Title>_Resume.pdf` (Portuguese: `..._Curriculo.pdf`).
- Cover letter: `<FirstName>_<LastName>_<Title>_Cover_Letter.pdf` (Portuguese: `..._Carta_de_Apresentacao.pdf`).
- The company name never appears in PDF file names.
- `<Title>` comes from the opening's title, shortened by the AI during keyword extraction and editable by the user; for a library document it is the focus. The name is the one printed on the resume, not the Clerk account name.
- File names use ASCII only: accents, cedillas and symbols are removed and spaces become `_`, since some applicant tracking systems and portals break on accented file names. Example: `Guilherme_Monte_Engenheiro_de_Software_Senior_Frontend_Curriculo.pdf`.
- The pattern is a suggestion: the user can edit the file name before downloading.
- An application can also be downloaded as one ZIP named `<Company>_<Title>.zip` (the applicant's convention, unlike the PDFs inside it), so that unzipping creates a folder named after the opening, which helps the user organize uploads across many applications. It holds the PDF of the official snapshot of every version of the application's documents, named as above (without the company). When two versions would get the same file name, the version's label is appended (`..._Curriculo_copia.pdf`).

## Writing style and tone

- **Style profile:** the user provides one to three samples of their own writing (an old cover letter, a post, a resume they like); when they provide none, the text of their profile serves as the sample. A cheap call extracts a style profile (sentence length, formality, preferred vocabulary, words to avoid, use of first person), which the user reviews and approves. It enters every generation as a style instruction and never copies sentences or facts from the samples.
- **Suggested tones**, chosen per document on top of the style profile: **Your style** (default), **Formal** (banks, government, traditional consultancies), **Direct** (startups, technical roles: short sentences, strong verbs, no adjectives), **Warm** (mission-driven organizations) and **Technical** (highly specialized roles: more domain vocabulary and numbers). When an opening is added, the AI suggests a tone from its description ("this is a traditional bank; we suggest Formal") and the user accepts or changes it. The choice is saved with the application. A tone changes form, never facts.

## Document workspace

A resume, a cover letter or the LinkedIn text opens in the same workspace as the profile (ADR 0009), for library documents, applications and the LinkedIn page alike.

- **Left:** the document's index (its sections and positions) and its findings: the code checks and the coverage review, each with Fix where code can fix it, “Talk to the agent” (the finding with its passage as the quote) and Ignore, as in the profile. Going to a finding, a review note or an index item scrolls to its passage and selects it; the active finding (the one opened, or under the pointer in the text) is marked in the list, and a row under the pointer lights its passage up.
- **Center:** the selected version's latest snapshot in its PDF look (the layout below: fonts, header, section titles, bullets), editable in blocks like the profile. **Everything is the user's to edit except the section titles** (the template's) and the credentials: the header (name, title line, contacts, city) and a position's employer, title, dates and context included. An edit that makes a fact differ from the profile is pointed out by the `lockedFact` finding (Ignore, Talk to the agent), never refused. Saving an edit creates a snapshot (origin edited, author user), coalesced while the user keeps typing. Hovering a line shows its trace.
- **Section order:** a resume's sections, each with its content, can be moved: before Experience, Projects, and so on (the header stays first). The order is the order of the snapshot's `sections`, so every snapshot carries it and the editor, the PDFs (every template), the plain text (ATS, copy, vectors), translation and adaptation (they keep the document's order) all follow it; no extra field is needed, and a document that was never reordered keeps the order generation gave it (the template's, with Projects right after Experience). Generation always uses that default; it never reorders on its own. The user reorders from the left index: each section has a drag handle and, as the accessible alternative, Move up and Move down buttons (visible on hover and on keyboard focus); a move is saved at once as a snapshot of its own (origin `edited`), so undo and the version history restore the previous order. **The agent** may suggest a move with `propose_section_move` (“move Projects above Professional experience”): the suggestion is a change like the others (stored with part `section:<kind>` and `above:<kind>` or `below:<kind>` as its replacement) shown as a banner on the section's title (“Suggested: move this section above Professional experience”, why, Accept, Reject); accepting creates a snapshot authored by the AI. Section order is not a locked fact, so it needs no request from the user; the agent leaves the order alone unless asked, or a different one clearly serves the opening. A move whose section already sits there, or whose sections are gone, is stale and can only be rejected; a newer move of the same section replaces a waiting one. The PDF's cache is keyed by snapshot, so a reordered document renders anew and the template version doesn't change.
- **Right:** the document agent, the PDF preview, and the versions with their change history.
- **The agent** knows what the generation used (the frozen profile version, settings, the opening's brief and fit check or the library focus, communication rules and public names, the coverage review, each line's trace) and reads any part of that profile version. A selected passage or a finding reaches it as an attachment. **It never modifies the document directly:** every change it makes, including one the user asked for (“add one more bullet to X”), is a suggestion in the text (word-level diff, Accept, Reject); accepting creates a snapshot. It can replace, remove or add lines (a bullet at the end of a position, after a given one, a paragraph of the letter). It grounds them on the profile and on what the user asks for in the conversation, and never invents: a figure must come from one of the two. **Locked facts** (the header, a position's employer, title and context): the agent may suggest changing one only when the user asked for that change in this conversation, never on its own judgement; code enforces it (the suggestion must quote the user's request, found in their messages, with the latest message about it) and otherwise tells the agent to ask the person first.
- **The user writes what they want.** The document isn't limited to the profile: a line the user types, or accepts from the agent, that doesn't trace to the profile version is pointed out as “not in your profile”, with **Add to the profile** (a suggestion in the profile's draft, origin `document`) and Ignore. Figures not marked `[medido]`, never-include terms and originals with a public name are pointed out the same way. These findings never block: the PDF asks for “Generate PDF anyway” while they are open.
- **Check against my profile.** A “not in your profile” finding offers **Check against my profile** (pt-BR “Verificar no meu perfil”), and the findings header offers it for all of them when there are several. The user adds the fact to the profile, publishes, and asks the system to look again, without regenerating anything. One small AI call (the classification role, like rewriting a gap answer; it spends no credit: the user's own key on a paid plan, else StoryToRole pays) reads every unbacked line against the profile **published now**, not only the version the document froze. For each line the model returns the profile lines that back it or none: every fact in the line must be stated by the lines it cites (same strict rules as generation: a figure only when the profile marks it `[medido]`, nothing the profile lists as not done, studied only or a known gap), and code drops a citation of a line that doesn't exist and any backing whose figures the cited lines don't give. The document moves to the published version as “Use version N” does (code re-traces the other lines), a backed line gets its trace (origin profile, cited ids), and a new snapshot (origin `rebased`) records the version used. The finding disappears. A line still unbacked keeps its finding, with a short “Still not in your profile: …” reason from the model (or the unmarked figure), shown until the line's text changes. A failed call changes nothing. There is no automatic check after an edit: it would spend a model call on every pause in typing, and a half-typed line is rarely worth checking; the button is the user's explicit ask.
- **A newer profile:** when a newer profile version is published, the document shows “Profile version N is newer than this document's” with **Use version N**: the document freezes the new version, its traces and findings rerun against it, lines the user had added to the profile stop being pointed out, and the code-printed fields the user left as printed are printed again, so a translations dictionary entry published since applies.
- Charged per message like the profile agent; one conversation per document, with New conversation and `/clear`.

## Trace in the editor

Hovering or tapping a line in the document editor shows where it came from: the passage of the profile version frozen in that document (its section and position, and the version's number and date), or "from this application's instructions". Lines the user typed in the editor are marked "written by you". **Editing a line keeps its trace:** a traced line the user rewords keeps its id and its sources, with origin `edited` (“From your profile, edited by you”); a change to spacing or punctuation alone isn't an edit. Only a line with no trace is “not in your profile”. Every line always shows a subtle origin marker (profile, application instruction, written by you, edited); there is no toggle. The trace appears only in the editor, never in the PDF.

## Global template

Each user has a global template that defines which sections their resume has. A section can be conditional:

- on the output language or market ("Personal details only in German resumes");
- on the opening's extracted keywords or the library document's focus ("Publications only when the opening mentions research").

Conditions are checked by code, so the result is predictable. In any application, the user can force a section in or out, like other per-application overrides. AI-suggested sections ("include Publications for this opening?") may come later if fixed rules are not enough. Sections come from a catalog. On by default: Summary, Skills, Experience, Projects, Education, Languages. Optional, off by default: Certifications, Publications, Awards, Volunteering, Courses. Projects prints only when the profile has projects (the profile's Projects section), right after Experience whatever the template's order when a document is generated (the user, or an accepted agent suggestion, may then move it, see Document workspace), and can be turned off like any section; a project is written like an experience of its age (bullets per the settings by its end date, each citing the project's own lines, figures only when marked measured, "what I did not do" never claimed), with its name, role, dates and link printed by code. A project is never written as a position, nor a position as a project. Resumes are kept within the length the generation settings allow (two pages by default), which is why optional sections start off; users who want one enable it, globally or per application. Sections draw on the profile's matching section (education, certifications, competencies by level, languages); a competency marked "studied" appears only when the opening asks for it and the user allows it.

## Layout

One layout in the MVP, modeled on the resumes of the meu-emprego-novo CLI (generated with ReportLab and already used in a real job search):

- A4, single column, Helvetica (regular, bold, italic), friendly to applicant tracking systems: no tables, columns, icons or images.
- Header: the name, large, bold, dark blue; a line with the target title and main technologies ("Senior React Native Engineer | React Native, Expo, TypeScript"); contacts separated by `|` (email, phone, LinkedIn, GitHub); the city.
- Section titles in uppercase dark blue with a thin rule below, named in the output language ("Professional experience", "Experiência profissional").
- Summary: one justified paragraph.
- Skills: one line per group with a bold label ("Core:", "Frontend:", "Testing:"), since applicant tracking systems scramble columns.
- Experience: company in bold on the left, period in grey aligned right, title in italics below with optional context in parentheses ("parallel project"), and bullets with a hanging indent, each following action, result and "Built with ...". Dates follow the output language ("Nov/2024 – Jul/2026", "nov/2024 – jul/2026").
- Projects: right after Experience by default (sections print in the snapshot's order); the project's name in bold on the left, period in grey aligned right, the role in italics below (like a title), the link in grey, then bullets like an experience's.
- Education and languages: compact lines with the institution in bold.
- The cover letter uses the same header (name, title line, contacts), then the letter body, on A4 in Helvetica.
- Length: as the generation settings set it (at most two pages for a resume and one for a cover letter by default), enforced as described there.
- PDFs are rendered from structured content in a task with a JavaScript renderer (for example `@react-pdf/renderer`) reproducing this look, since ReportLab is Python.
